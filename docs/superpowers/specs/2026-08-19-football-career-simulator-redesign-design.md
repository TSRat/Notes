# 《第 91 分钟》真实俱乐部球员职业生涯模拟器重设计规范

> - 状态：已完成对话设计审批，等待书面规范复核
> - 日期：2026-08-19
> - 适用代码库：`football-career-sim/`
> - 设计来源：用户提供的 Phase 3 Handoff、后续逐项选择，以及 2026-08-19 批准的五部分重设计
> - 冲突优先级：本规范在重设计范围内高于现有 `docs/sites/football-career-sim/` 文档；未冲突的性能、无障碍、隐私和交付约束继续有效

## 1. 产品定义

《第 91 分钟》是一款使用真实俱乐部世界作为情感舞台、使用模拟球员生态推动未来赛季的网页球员职业生涯游戏。玩家在 25–40 分钟内经历一名球员从 16 岁到退役的完整人生，在普通赛季自动推进与关键时刻决策之间交替。

它不是足球经理游戏、完整比赛操作游戏或分科足球百科。足球知识、俱乐部传统、国家队身份、合同、伤病、家庭与媒体等内容，都必须先成为同一名球员在某个时间点会遇到的具体处境，再进入游戏。

### 1.1 核心承诺

- **真实俱乐部世界**：真实俱乐部、联赛、城市、球场、竞争关系、历史身份和带核验日期的实力基线负责唤起情感。
- **模拟人物生态**：首发版本不使用真实现役球员、教练或管理人员；未来赛季的队友、对手、教练、经纪人和管理人员由模拟系统生成并持续演化。
- **事实明确、结果不确定**：玩家能看见合同、角色、赛程、竞争和已知风险，但看不到精确成功率；合理选择也可能因执行、队友、对手或有限随机波动而失败。
- **关键时刻决策**：普通比赛和月份快速模拟，只在足以改变职业轨迹的场上、转会、国家队或人生节点停下。
- **多种好人生**：世界级巨星只是少数结局。长期职业球员、小球队传奇、国家队英雄、升级功臣、漂泊后找到归属或伤病后重生，都可以是好结局。
- **足球主导、人生穿插**：关键内容约 70% 为足球、30% 为场外人生；场外事件必须能影响足球道路。

### 1.2 体验成功标准

一段生涯结束后，玩家首先记住的应是个人故事，而不是学习过哪些足球分类。例如：

> “我在豪门青训失败，被租借到荷兰，在日本重新成为核心，后来代表母亲的祖国参加世界杯。最高 OVR 只有 82，但退役赛上老东家的球迷仍在唱我的名字。”

产品的最高层验收标准是：玩家愿意立即创建第二名球员，尝试另一条人生。

### 1.3 非目标

- 不提供 90 分钟逐回合操作、手柄式动作系统或完整战术布置。
- 不让玩家管理俱乐部财政、球探部门、训练日程或全队转会。
- 不把百科、战术、商业、文化、医学等内容拆成独立课程。
- 不承诺复刻真实未来赛果，也不把模拟结果表述为预测。
- 首发版本不使用未经授权的真实队徽、球衣图案、球员肖像或官方摄影。
- 不采用付费抽卡、体力付费或通过降低成功率促成付费的机制。

## 3. 一段生涯的节奏

### 3.1 时间范围

- 常规起点为 16 岁。
- 退役年龄由位置、能力、伤病、角色与选择共同决定，通常为 32–39 岁。
- 一段完整生涯包含约 14–23 个赛季。
- 普通月份和低重要度比赛以短摘要推进；每个赛季只保留足以影响道路的停顿。

### 3.2 目标时长分配

| 环节 | 目标时长 |
| --- | ---: |
| 创建球员 | 2–4 分钟 |
| 青训与职业突破 | 5–7 分钟 |
| 稳定一线与巅峰 | 12–20 分钟 |
| 转折、晚期与退役 | 5–7 分钟 |
| 终章与生涯博物馆 | 2–3 分钟 |

标准生涯约有 30–40 次关键职业决策、6–10 场可交互关键比赛。系统必须允许快速阅读者在约 25 分钟完成，也允许阅读俱乐部上下文和赛季年鉴的玩家停留至约 40 分钟。

### 3.3 赛季闭环

```text
赛季简报
→ 普通比赛与月份快速推进
→ 关键事件暂停
→ 可选的关键比赛
→ 转会或国家队窗口
→ 赛季年鉴
→ 下一赛季
```

每次暂停只提出一个主要问题。百科解释、俱乐部背景和人物意见作为上下文出现，不与主要操作争夺层级。

### 3.4 生涯阶段

1. **起点与青训**：身份、位置、初始特质、第一家青训机构。
2. **职业突破**：首份合同、租借、替补出场、位置竞争和首次媒体关注。
3. **稳定一线**：首发地位、战术角色、续约、转会兴趣、国家队边缘位置。
4. **巅峰与选择**：争冠、欧战或洲际赛事、国家队大赛、豪门机会、领导责任。
5. **转折与适应**：教练更替、重伤、错误转会、状态下降、改打新位置或跨洲发展。
6. **晚期与传承**：降低角色、回归旧队、带领年轻人、国家队告别、退役与第二职业。

阶段是时间位置，不是内容分类。同一个伤病主题可以在青训阶段表现为成长负荷，在巅峰阶段表现为赛程风险，在晚期表现为是否接受新的比赛角色。

## 4. 创建球员

创建流程使用连续登记卡，不使用一张包含所有字段的长表单。

### 4.1 四步流程

1. **身份**：姓名、主要国籍、可选第二国籍或家庭背景、出生地、惯用脚。
2. **足球起点**：主要位置、次要位置、身体轮廓、童年支持的俱乐部、青训路径。
3. **成长特质**：选择一个具有优势与代价的起始特质。
4. **生涯基调**：故事、标准或漂泊模式。

可用特质示例：

- 天赋出众：初始技术更高，外界期待和早期压力更高。
- 晚熟球员：初始 OVR 较低，成长窗口更长。
- 街头足球：创造力较强，早期战术纪律较弱。
- 教练之子：战术理解较强，更容易遭遇关系背景质疑。
- 双国籍家庭：国家队道路更多，未来可能面对身份抉择。

### 4.2 难度语义

- **故事模式**：降低严重负面事件的连锁强度，提高复苏机会；不保证成为球星。
- **标准模式**：采用本规范的默认概率校准。
- **漂泊模式**：合同、伤病、阵容竞争和文化适应的容错更低；仍保留可达的好结局。

完成四步创建后进入青训起点选择；确认第一家俱乐部后生成 16 岁球员登记卡，明确显示初始 OVR、主要与次要位置能力、第一家俱乐部和核心特质。

首发位置覆盖门将、边后卫／翼卫、中后卫、防守中场、中前卫、攻击中场、左右边锋和中锋。界面使用熟悉的足球缩写，模拟层同时记录位置族和左右侧，避免为每个位置复制一套规则。

“童年支持的俱乐部”是情感、媒体和潜在成就变量，不保证玩家从该俱乐部青训出发。第一家青训俱乐部根据出生地、国籍、背景和模式生成一组合理起点，由玩家在首个职业事件中确认；故事模式可以提供更宽的起点选择，标准与漂泊模式更受地域和招募条件约束。

## 5. 真实世界与模拟生态

### 5.1 真实数据边界

首发版允许以真实世界事实呈现：

- 俱乐部、联赛、足协和国家队名称；
- 国家、城市、球场名称与地理关系；
- 俱乐部传统色、历史身份、主要竞争关系和历史声望；
- 当前赛季的实力基线、赛事结构、注册规则和国家队窗口；
- 经核验的青训、招募、战术或治理特征。

每项可能变化的事实必须附 `asOf`、`sourceRefs` 和 `confidence`。当前赛季以后，积分、冠军、升降级、教练任命、球员流动和比赛结果均明确属于模拟世界。

### 5.2 首发全球网络

首发深度生态为 15 个：

- 欧洲：英格兰、西班牙、德国、意大利、法国、葡萄牙、荷兰、比利时；
- 亚洲：中国、日本、韩国、沙特阿拉伯；
- 美洲：巴西、阿根廷、美国。

目标为 120–160 家深度俱乐部。其他地区通过国家队比赛、转会市场和低细节俱乐部节点进入世界，不要求首发时拥有同等事件密度。

“深度俱乐部”至少需要：真实身份资料、可核验的足球特征、压力和发展环境、俱乐部专属处境、2–4 个专属成就，以及一组不会把俱乐部简化为刻板标签的文案规则。

### 5.3 模拟人物

每家活跃俱乐部维持约 22–28 名模拟球员，并按赛季生成、成长、转会和退役。模拟教练至少拥有：

- 战术偏好；
- 对年轻人的使用意愿；
- 轮换倾向；
- 沟通和媒体风格；
- 位置需求；
- 工作稳定度。

经纪人、队医、管理者、队友与家庭成员只建模对职业选择有影响的属性，避免生成无用途的复杂人物档案。

全球生态使用三级模拟精度：玩家所在俱乐部、直接对手和当前赛事采用完整阵容与比赛级模拟；被转会、国家队或洲际赛事观察到的联赛采用赛季级模拟；其余网络只保存实力、排名、升降级和关键人物摘要。背景节点进入玩家视野时，系统根据原始种子和既有赛季记录确定性展开，不能因为打开页面而改变历史。这一策略保证全球情感网络存在，同时避免把首发包和存档膨胀成足球经理数据库。

### 5.4 未来真实人物入口

人物统一通过 `FootballPerson` 接口接入：

```ts
type PersonType = 'player' | 'coach' | 'executive' | 'agent' | 'medical'
type DataMode = 'simulated' | 'real' | 'historical'

interface FootballPerson {
  id: string
  personType: PersonType
  dataMode: DataMode
  displayName: string
  nationalities: string[]
  careerHistory: CareerHistoryEntry[]
  externalIds?: Record<string, string>
  dataVersion: string
  sourceRefs: string[]
  rightsStatus: 'clear' | 'name-only' | 'restricted' | 'unknown'
}
```

首发 UI 不暴露空入口，但存档、事件和人物关系不得假设所有人物都是虚构人物。未来可选择“模拟生态”或“真实赛季快照”，并通过 `dataMode`、数据版本和权利状态隔离。

## 6. 国家队生涯

国家队不是额外小游戏，而是与俱乐部共用年龄、体力、状态和时间线的第二条职业线。

### 6.1 资格与征召

球员创建时记录主要国籍、第二国籍、出生地和可能的协会资格。征召综合：

- 俱乐部出场时间和近期表现；
- 所在联赛级别；
- 同位置竞争与国家队教练偏好；
- 健康、疲劳和赛程；
- 已锁定或仍可变更的协会资格。

资格与更换协会规则必须使用当期 FIFA 官方来源，不根据文学作品或旧规则推断。

### 6.2 国家队节点

- 青年国家队邀请；
- 首次成年队征召；
- 双国籍选择或符合规则的协会变更；
- 友谊赛、预选赛、洲际杯和世界杯；
- 最终名单、替补落选、关键淘汰赛；
- 队长责任、告别或重新征召。

国家队经历会影响曝光、疲劳、伤病、转会兴趣和生涯遗产，但不是好结局的必要条件。

## 7. 球员能力与 OVR

### 7.1 展示层

玩家持续可见：

- OVR 1–99；
- 年龄和位置；
- 俱乐部角色；
- 近期状态、体力和教练信任；
- 市场关注和国家队地位。

OVR 建议解释区间：

| OVR | 直观含义 |
| ---: | --- |
| 40–54 | 青训、半职业或职业边缘 |
| 55–64 | 低级别职业球员或顶级联赛年轻替补 |
| 65–72 | 稳定职业球员或顶级联赛轮换 |
| 73–79 | 顶级联赛首发级别 |
| 80–84 | 联赛球星或强队核心 |
| 85–89 | 世界级球员 |
| 90–93 | 金球级表现层次 |
| 94–99 | 时代传奇 |

### 7.2 计算原则

OVR 由位置加权的长期能力构成，包括技术、传球、射门、防守、身体、速度和比赛阅读等基础域。主要位置和次要位置分别计算评分。

OVR 不直接包含状态、媒体热度、俱乐部声望、短期教练信任或国家队知名度。因此 OVR 76 的状态球员可以压过 OVR 80 的竞争者，OVR 84 的球员也可能因战术不适配失去首发。

重要变化必须解释来源，例如：

> OVR 74 → 76：比赛阅读 +2、弱势脚 +1、右边锋熟练度提升。

### 7.3 成长与衰退

成长由出场、比赛级别、训练环境、教练培养倾向、位置稳定、职业习惯、伤病、适应和挑战强度共同决定，不使用一条统一年龄曲线。球员可以早熟、正常成长或晚熟。

衰退按能力结构发生：速度型边锋可能先失去爆发，中场可以通过阅读比赛延长巅峰，中后卫和门将可能更晚成熟。严重伤病可以改变真实能力结构，而不只是永久扣除一个总数。

## 8. 决策与结果引擎

### 8.1 决策信息的四层结构

每个重大选择必须依次提供：

1. **确定事实**：合同、角色、阵容、赛程、联赛、地点、伤病状态等。
2. **人物表达**：经纪人、教练、家人、队友或媒体的有立场意见。
3. **玩家行动**：通常为三个真正不同的选择；特殊场景可为两个或四个。
4. **不确定结果**：只描述风险性质，不显示“72% 成功率”。

选择不得使用模糊同义项制造假选择，也不得总有一个同时增加所有数值的最优答案。

只有场上瞬间、紧急医疗沟通或明确有时间压力的事件使用 5–15 秒实时倒计时。转会、合同、国家队身份和家庭决定默认不使用实时倒计时，玩家可以阅读事实后再选择。计时压力不能成为隐藏信息或跳过无障碍内容的理由。

### 8.2 结果公式

```text
基础能力
＋近期状态
＋体力与伤病
＋位置和战术适配
＋教练安排与队友环境
＋对手强度和比赛上下文
＋玩家选择修正
＋受控随机波动
```

OVR 提高成功范围，但不直接指定结果。每次结果写入解释记录，至少能回答“哪些已知因素帮助或阻碍了这次行动”。前台使用自然语言解释，不公开内部权重。

### 8.3 随机与可复现性

- 新生涯生成 `careerSeed`。
- 伪随机数状态与存档同步，刷新页面不能无限重抽同一次结果。
- 同一随机种子与相同事件日志可用于测试和错误复现。
- 选择改变结果分支；系统不要求不同选择复用同一结果。
- 随机波动设置上限，避免低概率事件持续覆盖长期能力与合理决策。

### 8.4 即时与延迟后果

即时反馈显示比赛、关系、状态或属性的已知变化。重要选择还可以写入 `consequences` 队列，在数周、数月或数年后触发，例如：

- 当年拒绝外租导致教练印象变化；
- 曾经帮助过的年轻队友在多年后成为国家队竞争者；
- 一次带伤出场改变长期伤病风险；
- 与旧俱乐部的离队方式影响未来回归。

延迟后果触发时必须提供回溯提示，让玩家知道它与哪次旧选择有关。

## 9. 比赛系统

### 9.1 普通比赛

普通比赛按球队实力、战术匹配、阵容、球员角色、状态与随机种子模拟，输出短摘要和位置相关统计。系统只把里程碑、异常表现和职业影响显著的比赛提升到时间线。

### 9.2 关键比赛

关键比赛隐藏常规导航，只保留比分、时间、比赛双方、球员任务、体力、信心、黄牌、教练信任和文字播报。每场包含约 2–4 个决策。

场景必须与位置有关。例如同一比分下：

- 边锋决定继续压迫、保留体力、内收接球或攻击疲劳边后卫；
- 中后卫决定上抢、保护身后、指挥越位或接受战术犯规风险；
- 中场决定控制节奏、直塞、回撤保护或主动要求换人；
- 门将决定快速发动、压低节奏、出击或留在门线。

结果反馈区分：即时比赛后果、人物反应、状态变化和潜在长期影响。比赛失败不自动等于选择错误。

## 10. 转会、合同与俱乐部角色

报价由表现、年龄、合同期限、俱乐部竞技目标、财力、位置需求、教练战术、联赛注册规则、经纪人网络、国家队曝光和适应因素共同生成。

每份报价明确展示：

- 真实俱乐部和联赛；
- 合同年限与薪资级别；
- 预计角色而非保证角色；
- 教练计划和阵容竞争；
- 竞技目标；
- 可确认的城市、文化和生活信息；
- 已知注册或国家队影响。

可选道路包括留队竞争、外租、主动申请转会、降薪换取机会、等待自由身、回归旧队、前往非主流联赛成为核心。系统不得把“加盟名气更大的俱乐部”固化为最优解。

## 11. 足球与人生

人生事件约占关键事件的 30%，但每项必须改变球员的职业条件或对结局的评价。范围包括：

- 家庭对迁居和转会的态度；
- 语言与文化适应；
- 经纪人信任；
- 媒体和社交媒体压力；
- 财务安全；
- 伴侣、子女与照顾责任；
- 伤病期间的心理状态；
- 队内友谊、冲突和领导责任；
- 家乡、公益和退役准备。

不建立独立恋爱、房产、消费或社交媒体数值经营系统。人生内容通过 `wellbeing`、关系、适应、财务安全、可用选择和结局权重影响足球生涯。

## 12. 结局与概率校准

### 12.1 结局构成

结局由五个维度共同生成：

- 竞技高度；
- 职业长度；
- 俱乐部归属；
- 国家队遗产；
- 人生完整度。

系统先计算维度，再从满足条件的结局叙事中选择最匹配的主结局和一至两个副章。允许的好结局包括世界级巨星、一人一城、国家队英雄、小球队升级功臣、跨洲漂泊后找到归属、伤病后复出、长期可靠职业球员、青训失败后证明自己，以及在竞技巅峰前离开但拥有完整生活。

### 12.2 标准模式校准目标

- 55%–65% 的完整生涯获得至少一种好结局；
- 10%–15% 成为联赛或国家队级球星；
- 2%–4% 进入时代传奇层级；
- 其余为普通、遗憾或苦涩结局，但仍可形成独特传记与成就。

这是批量模拟的验收区间，不是单局承诺，也不向玩家显示。好结局与球星不是同一维度：提高生活完整度不应自动提高 OVR，成为巨星也不能保证人生完整。

### 12.3 防止成功膨胀

- 冠军和奖项受球队实力、竞争和出场贡献共同约束。
- 豪门板凳不会因俱乐部冠军自动获得核心荣誉评价。
- 关键选择提供概率修正，不直接授予球星身份。
- 高 OVR 仍需稳定出场、健康和合适环境才能转化为声望与荣誉。
- 传奇级结局需要多个赛季和多个维度的持续证据。

## 13. “生涯印记”成就系统

成就不直接提高 OVR、属性或成功率，避免元进度破坏单局公平。奖励用于扩大叙事选择和收藏表达。

### 13.1 四类成就

1. **里程碑**：首次首发、百场、首次国家队征召、首个冠军等清晰节点。
2. **生涯路线**：奖励独特道路，例如“一城一生”“他们曾经放弃你”“租借生的春天”“三大洲的更衣室”“没有豪门也很好”。
3. **比赛与位置**：奖励具体足球经历，例如“十分钟改变一生”“十二码孤岛”“沉默的发动机”“错误之后”“宿敌记住了你”。
4. **隐藏人生印记**：结算或满足条件后揭示，例如“旧伤新生”“两个祖国之间”“最后一次首发”“没有金球也是一生”“经纪人没有替你决定”。

### 13.2 专属成就

每家深度俱乐部配置 2–4 个、每支重点国家队配置 1–3 个专属成就。专属条件必须来自可核验的历史、文化、青训、竞技或球迷身份，不得仅凭“传控”“铁血”“豪门压力”等刻板词生成。

### 13.3 奖励

允许解锁：

- 新的起始背景或带代价特质；
- 挑战模式；
- 时间线和传记版式；
- 特定阶段的情景开局；
- 博物馆陈列主题。

首发内容目标：30 个基础里程碑、40 个生涯路线、30 个比赛与位置、20 个隐藏成就，另加俱乐部与国家队专属成就。

### 13.4 生涯博物馆

博物馆跨存档保存已完成人生，包括传记封面、时间线、巅峰 OVR、俱乐部地图、国家队经历、重大选择、成就和结局。比较功能使用多维画像，不按冠军或 OVR 生成单一总排行榜。

## 15. 视觉与交互方向

### 15.1 视觉主题

视觉主题为“球员档案 × 比赛日转播 × 更衣室生涯墙”。基础使用炭黑和球场暗绿，当前俱乐部传统色作为动态强调色。合同、球票、比赛名单、储物柜铭牌和新闻剪报用于建立足球语汇，但每个装饰元素都必须承担状态、时间或身份信息。

不得回到通用霓虹数据仪表盘，也不得让三本 Notebook 重新成为三块常驻并列面板。

### 15.2 字体与颜色

- 中文正文：`PingFang SC`、`Microsoft YaHei`、系统无衬线回退。
- 数值和界面：`Inter`，表格数字使用等宽数字特性。
- 赛果、重大新闻和章节数字：`Anton`，仅用于短文本。
- 基础背景、面板和文字沿用既有暗色令牌；俱乐部主色、副色和 glow 由主题数据注入。
- 主题切换必须检查文字对比度；不能假设俱乐部主色可直接承载黑字或白字。

### 15.3 品牌与权利

首版使用真实俱乐部名称、城市、文字标识和经核验的传统色，不使用真实队徽、球衣图案、人物肖像或未经授权图片。数据模型保留 `brandAsset` 与 `rightsStatus`，未来获得授权后可替换文字标识，不改变布局。

### 15.4 动效

- 普通月份快速翻动，关键事件减速并展开。
- 合同卡从对应时间节点展开。
- 国家队征召使用电话或名单公布的视觉语法。
- OVR 变化使用克制的数字滚动和轮廓高亮。
- 重大进球可短暂冻结比分并表现看台声浪，但不自动播放声音。
- 重伤、落选和解约使用留白、低饱和和节奏变化，不使用夸张故障特效。
- 转会后全局俱乐部主题约在 600ms 内完成过渡。
- `prefers-reduced-motion` 下取消滑动、缩放和连续宽度动画，只保留即时状态变化与文字倒数。

## 16. 响应式与无障碍

### 16.1 桌面

桌面使用一个约 760–900px 的主舞台与一个按需出现的上下文侧栏。侧栏关闭后主舞台居中扩展。不得恢复固定 300px／自适应／350px 的三屏常驻结构。

### 16.2 平板

时间线保持单主列，上下文作为右侧抽屉。球员概要可压缩但 OVR、年龄、俱乐部、体力和下一节点保持可见。

### 16.3 移动端

普通阶段提供四项底部导航：生涯、球员、世界、博物馆。进入关键决策、合同谈判或比赛后自动隐藏，形成单任务界面。上下文使用底部抽屉；核心操作位于拇指可达区域。

- 320px 宽度无横向滚动；
- 使用 `100dvh` 和安全区域；
- 最小触控目标 44×44px；
- 不能只通过 hover 提供信息；
- 键盘和触屏均能退出沉浸页面。

### 16.4 倒计时与辅助技术

压力倒计时同时提供视觉条、数字和屏幕阅读器文本。读屏提示按有意义的阈值播报，避免每秒打断；推荐在 10、5、3、2、1 秒提示。减少动效时视觉条变为静态文字倒数。

所有决策、导航和抽屉使用语义元素，焦点可见。打开弹层后焦点进入，关闭后返回触发点。比赛比分、赛季变化和 Toast 分别使用恰当的 live region，避免重复播报。

### 17.1 分层

```text

模拟世界层
```

组件只消费经选择器整理的视图模型，不直接修改原始 JSON 或实现概率计算。

### 17.2 关键实体

除 `FootballPerson` 外，至少需要：


`WorldSnapshot` 保存基线之上的稀疏赛季变化、当前活跃实体和可重建摘要，不复制静态俱乐部内容包。背景生态可以从 `careerSeed`、内容版本和事件日志重建，已进入玩家视野并影响选择的事实必须固化，避免内容重载后改变既有生涯。

事件模板使用条件、上下文槽位、选择和后果定义，不直接写死某个俱乐部一定发生某个故事。俱乐部专属事件可以绑定俱乐部包，但仍须检查赛季、人物和职业阶段条件。

### 17.3 引擎边界

- `worldEngine`：赛季、赛程、俱乐部实力、阵容和模拟人物演化。
- `careerEngine`：年龄、能力、角色、合同、关系和成长。
- `matchEngine`：普通比赛与关键时刻计算。
- `eventEngine`：事件资格、优先级、去重和延迟后果。
- `transferEngine`：报价、角色和适配生成。
- `nationalTeamEngine`：资格、征召、赛事窗口和名单。
- `achievementEngine`：单局成就检测与博物馆解锁。
- `endingEngine`：五维结局评价和传记生成。
- `saveRepository`：版本化存档、迁移、恢复和导入导出。

每个引擎接受显式状态和随机源并返回结果，不直接访问 React、DOM 或 `localStorage`，以支持批量模拟和单元测试。

### 17.4 当前实现迁移

可以保留：React、TypeScript、Vite、React Router、Lucide、本地字体、i18n 字典和静态部署方式。

需要替换或重构：

- 现有六数值 `PlayerState` 扩展为展示层与模拟层分离的能力模型；
- 现有一次性 `ChoiceEffect` reducer 改为命令、结果和事件日志；
- `career-experiences.json` 从可浏览的 56 项目录改为事件模板与上下文标签；
- 三栏 `CareerPage` 改为连续时间线与按需上下文；
- `/database` 降级为兼容入口和事件内解释层；
- 加入创建、赛季年鉴、世界页和生涯博物馆；
- 存档增加版本、随机状态、世界快照、延迟后果和迁移逻辑。

重构必须通过新引擎与适配器逐步替换，避免让页面组件成为模拟逻辑的新容器。

## 18. 存档、错误与恢复

### 18.1 存档

- 每次重大选择、赛季推进和关键比赛后自动保存。
- 首发使用 IndexedDB 保存版本化生涯、世界增量和博物馆记录；`localStorage` 只保存偏好、最近存档 ID 和轻量恢复指针，不要求账户。
- IndexedDB 不可用时切换到内存会话并立即提示导出，不假装已经持久保存。
- 保存当前生涯与独立博物馆索引；删除当前生涯不得同时删除已完成博物馆记录。
- 提供 JSON 导出与导入入口，便于玩家迁移和错误报告。
- schema 变更必须提供迁移函数；无法迁移时保留原始备份并解释原因。

### 18.2 异常处理

- 内容 ID 缺失：跳过该可选事件，写入诊断信息并继续推进；不能让生涯卡死。
- 俱乐部数据缺失：使用明确标识的低细节回退资料，不编造真实事实。
- 存档损坏：停止覆盖，保留原始数据，提供恢复上一自动存档、导出和新建生涯。
- 无可用事件：生成合规的普通赛季摘要并推进到下一固定节点。
- 未知比赛或赛季路由：展示原因、当前存档状态和安全返回路径。
- 计时结束：禁用未选选项，按该事件定义的“未行动”分支结算；不得随机替玩家点击某个表述性选择。
- 外部资料链接失效：游戏内容仍可运行，来源面板标记待复核。

## 19. 资料与内容工作流

### 19.1 权威层级

| 层级 | 用途 |
| --- | --- |
| S：当前官方规则、赛事规程、官方技术和医学报告 | 硬事实、资格、赛制、注册、医疗边界 |
| A：学术手册、同行评审研究、正式机构研究 | 商业、治理、训练、文化、伤病和发展框架 |
| B：公认的战术、经济与历史著作 | 长期模式、战术演变、足球经济和历史解释 |
| C：俱乐部／国家叙事、传记和可靠报道 | 身份、语气、人物视角和地方记忆 |

小说、回忆录、旧版规则、儿童读物和学生论文可以提供视角或线索，不能单独承担当前硬事实。

### 19.2 双入口规则

- 内容制作请求中由用户指定资料时，该资料拥有叙事解释优先权；系统补充当前官方、学术或统计来源并做交叉核验。
- 用户未指定时，由内容制作流程按权威层级选择最适合该主题的资料。
- 当前官方规则与法规在硬事实冲突时优先于历史著作。
- 每个系统或深度俱乐部建议使用“1 个当前官方来源＋1 个学术／统计来源＋1–3 个相关战术、历史或俱乐部著作”。

- 国家和地区：`La Roja`、`Futebol Nation`、`Angels with Dirty Faces`、`Feet of the Chameleon`、`Football in Asia` 等对应资料。

## 20. 本地化、分析与隐私

### 20.1 本地化

首发只交付简体中文，但所有界面文案通过 i18n 字典读取。内容数据使用稳定 ID，叙事文本与模拟参数分离，为未来英文版本预留。球员、俱乐部和比赛名称保留规范中文名与原文名字段。

### 20.2 分析

只记录关键人生选择和匿名玩法平衡事件，例如：

- `career_started`；
- `career_key_choice_made`；
- `career_key_match_completed`；
- `career_transfer_accepted`；
- `national_team_committed`；
- `career_completed`；
- `achievement_unlocked`。

首发可以继续只发出本地事件，不连接第三方。未来接入分析服务时必须获得明确配置，并禁止采集姓名自由文本、设备指纹、精确位置、联系人、广告标识和跨站行为。停留时间不能单独作为“沉浸感”成功证据。

## 21. 性能预算

- LCP 目标低于 1.5 秒；
- 交互延迟目标低于 100ms；
- 核心 JS 未压缩低于 500KB；
- 初始路由不加载完整全球俱乐部、博物馆和全部事件文本；
- 内容包和非当前路线按需加载；
- 不引入 3D、重量级图表或运行时富文本框架；
- 字体仅加载实际使用的字重，中文优先使用系统字体；
- 无网络和外部来源失效时，已安装的本地游戏内容仍可完整运行。

## 22. 测试与平衡验证

### 22.1 单元测试

- OVR 位置权重与上下限；
- 成长、衰退和伤病对能力结构的影响；
- 随机种子可复现；
- 事件资格、去重和延迟后果；
- 转会报价与角色约束；
- 国家队资格和征召边界；
- 成就条件与隐藏状态；
- 结局五维计算；
- 存档迁移和损坏恢复。

### 22.2 内容契约测试

- ID、引用和来源完整；
- 每个事件有事实、选择、结果解释和安全退出；
- 深度俱乐部满足资料与专属内容下限；
- 专属文案不依赖无来源刻板标签；
- 所有术语至少从一个真实生涯处境可达；
- 高风险医学、规则和合同内容具有当前官方来源与边界提示；
- 所有 UI 文本可从 i18n 字典加载。

### 22.3 批量模拟

使用固定种子批量运行标准模式，检查：

- 完成时长和关键事件数量；
- 好结局、球星和传奇比例是否落在目标区间；
- 不同位置、国籍、起点和俱乐部生态的成功差异是否可解释；
- 是否存在单一最优特质、选择或转会策略；
- 豪门板凳、低级别核心和跨洲路线是否都有可行结局；
- 伤病和随机事件是否过度连续终止生涯。

### 22.4 界面初步检查

- 320、390、768、1024、1440px 宽度；
- 首页、创建、时间线、关键决策、比赛、赛季年鉴、世界、博物馆；
- 首次进入、继续存档、空博物馆、损坏存档、未知比赛、倒计时结束；
- 键盘、焦点恢复、读屏播报、减少动效、高对比和 200% 缩放；
- Mobile Safari 安全区域和动态视口；
- 俱乐部主题切换后的对比度和焦点态；
- 关键链接和精确提交预览。

这些属于 Codex 初步证据，不能替代 Antigravity 的最终完整验证。

## 23. 实施分解

该设计是一个完整产品范围，实施计划应按可验证纵向切片展开，而不是同时大规模编写页面与 160 家俱乐部内容。

1. **模拟内核与版本化数据**：随机源、存档、球员、世界、赛季和事件接口。
2. **完整单人生涯纵切**：创建、时间线、关键选择、比赛、赛季年鉴、结局和博物馆全部可走通。
3. **国家队与转会生态**：双国籍、征召、赛事窗口、真实俱乐部报价与模拟阵容。
4. **成就与多结局平衡**：完整生涯印记、博物馆和批量模拟校准。
5. **全球内容扩展**：按资料包逐步达到 15 个生态和 120–160 家深度俱乐部。
6. **视觉、响应式与无障碍硬化**：全部路线、状态、性能和真实浏览器初检。
7. **精确提交预览与 Draft PR 更新**：保持当前 PR 为草稿，不自动合并，交回 Antigravity 做 Stage 3 验证。

每个切片都必须保持可构建、可测试和可继续游玩，不允许先建立大量空路由或空俱乐部占位后再补核心闭环。

## 24. 最终验收清单

- [ ] 一段标准生涯可在 25–40 分钟完成。
- [ ] 玩家在一分钟内理解 OVR、角色、俱乐部和当前处境。
- [ ] 生涯包含约 30–40 次关键决策和 6–10 场关键比赛。
- [ ] 真实俱乐部之间存在可感知、可追溯且不刻板的差异。
- [ ] 普通赛季快速推进，主要界面不再是内容百科或三屏信息墙。
- [ ] 每个重大选择均满足“事实明确、结果不确定”。
- [ ] OVR 重要但不能单独决定首发、比赛或结局。
- [ ] 国家队与俱乐部共用时间、体力和职业后果。
- [ ] 人生事件不脱离足球职业主线。
- [ ] 不成为巨星仍有多种令人满意的结局。
- [ ] 标准模式的批量模拟落在好结局、球星和传奇概率目标内。
- [ ] 生涯印记不提供属性或概率加成。
- [ ] 未授权真实队徽、球衣、肖像和摄影不进入首发资产。
- [ ] 存档可版本迁移，刷新不能重抽同一结果，损坏时不覆盖原数据。
- [ ] 320px 移动端无横向溢出，关键操作可单手完成。
- [ ] 键盘、读屏、减少动效和安全退出均可用。
- [ ] 核心包、LCP 和交互延迟满足预算。
- [ ] 关键事实具有来源、版本和核验日期。
- [ ] 当前 Draft PR 保持未合并，最终完整验证状态为 `ANTIGRAVITY_FINAL_VALIDATION: PENDING`，直到 Antigravity 返回结果。

## 25. 书面规范结论

本规范中的核心产品决定均已明确。后续实施可以在不重新打开概念选择的前提下，先编写详细实施计划，再按纵向切片改造现有 React/Vite 项目。若实现中发现真实数据权利、当前赛事规则或外部资料不可用，只缩小对应数据或资产的呈现方式，不替换已经批准的核心玩法与体验方向。
